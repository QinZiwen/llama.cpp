# 苹果 M2 上 llama.cpp PP 阶段 MUL_MAT 瓶颈分析

> **报告性质**:Experiment 001 交付物(里程碑 C) | 2026-08-31
> **硬件**:Apple M2 Air(8 核 GPU,统一内存 100 GB/s)
> **模型**:Llama-3.2-1B-Instruct-Q4_K_M(762.81 MiB)
> **原始实验日志与全部数据**:见 [analysis.md](./analysis.md)
> **阅读目标**:即使你不懂 GPU 性能工程,也能逐句看懂"我们测了什么、每个数字说明什么、为什么能得出这个结论"。

---

## 摘要:我们问了什么问题,答案是什么

**问题**:在这个 M2 上跑 llama.cpp,预填充阶段(PP)的矩阵乘法(MUL_MAT)到底慢在哪?kernel(内核)优化还有没有空间?

**一句话答案**:**PP 阶段 MUL_MAT 占了 87% 的时间,是算力受限(compute-bound)而非带宽受限,但真正导致"算力没跑满"的原因不是大家最常怀疑的"反量化计算"(dequant,只占 ~11%),而是矩阵乘指令本身的利用率——即使把权重换成不反量化的 F16(16 位浮点),利用率也只有 38%。** 所以"优化反量化"不是一个划算的方向,PP 侧进一步优化的空间被证实在边际化。

**读完这份报告,你会得到**:一条步步可验证的分析链、一张精确的成本分解表、以及"哪些优化值得做、哪些不值得"的明确结论。

## 一、背景:先把问题讲清楚

### 1.1 我们遇到的问题

LLM(大型语言模型)推理分两个阶段:

- **PP(Prompt Processing,预填充)**:一次性读完你的整段输入提示词,并把它转换成内部表示。特点是**一次性算很多**——假设提示词有 512 个 token(词元),就要同时算 512 行数据。
- **TG(Token Generation,逐词生成)**:一个 token 一个 token 地往外吐字。特点是**每次只算一个 token,但要从内存里搬很多数据**。

这俩的瓶颈天然不同:PP 像"工厂机器加工慢"(算力受限),TG 像"原料搬运慢"(带宽受限)。本报告只讲 PP。

### 1.2 为什么是 MUL_MAT(矩阵乘法)

LLM 的内部结构是很多层神经网络,每一层主要就干一件事:**把一个输入向量和一个权重矩阵相乘**(MUL_MAT)。模型越大、层越多,矩阵乘法占比越高。我们先用数据确认这一点(见第三节)。

### 1.3 四个必须懂的概念(小白补课)

1. **算力利用率**:GPU 有一张"理论最快速度"的说明书(峰值算力,单位 FLOPS,每秒浮点运算次数)。利用率 = 实际达到的速度 ÷ 理论峰值。就好比发动机标称 300 马力,实际只输出 90 马力,利用率 30%。**利用率低 = 发动机没使上劲**。
2. **compute-bound(计算受限)vs memory-bound(带宽受限)**:判断瓶颈靠"算术强度(AI, Arithmetic Intensity)"——**每搬运 1 字节数据,GPU 要执行多少次运算**。如果这个比值很高(每次搬运都伴随海量运算),瓶颈是"算不过来"(compute-bound);如果很低(搬很多数据却只算一点点),瓶颈是"搬不过来"(memory-bound)。
3. **量化与反量化(dequant)**:模型权重为了省内存,常被压缩存储。Q4_K 是"每个权重只占 4 位(bit)"的压缩格式。但 GPU 计算时要用 16 位浮点,所以**每次计算前都要先"解压缩"(反量化)**。这个解压缩动作本身要花时间——这正是我们怀疑的对象之一。
4. **F16(16 位浮点)**:不压缩的权重格式。用它不用反量化,但内存占用是 Q4_K 的 ~3 倍。

## 三、第 1 步:热点定位(profiling,性能剖析)

### 本节要回答的问题
整个 graph(计算图,模型的一次前向计算)里,时间都花在哪些运算上了?

### 方法
给 llama.cpp 加了一个轻量插桩(profiling):通过它提供的 `cb_eval` 回调,让每个运算节点单独计时,最后统计出"每个运算类型花了几毫秒、占比多少"。为了公平,我们把纯"搬数据/改形状"的元运算(RESHAPE/VIEW/PERMUTE 等,实际执行时几乎不花时间)从统计里过滤掉了。

### 数据
`LLAMA_OP_PROFILE=1`,输入 512 token 的提示(记为 pp512):

| 运算 | 调用次数 | 耗时(ms) | 占比 |
|---|---|---|---|
| **MUL_MAT(矩阵乘法)** | 226 | **1028.8** | **87.3%** |
| FLASH_ATTN_EXT(注意力) | 32 | 48.3 | 4.1% |
| GLU(门控线性单元) | 32 | 25.8 | 2.2% |
| ADD(加法) | 64 | 23.0 | 1.9% |
| RMS_NORM(归一化) | 66 | 18.4 | 1.6% |

### 怎么看这张表
- **MUL_MAT 一骑绝尘,占 87.3%**。第二名(注意力)只有它的 1/20。
- 这张表说明一件事:**想让 PP 变快,几乎唯一值得动的就是 MUL_MAT。** 就算把其他所有运算优化到零,也只快 13%。

### 本节结论
**优化目标锁定为 MUL_MAT。** 下一个问题:它为什么慢?是算力受限还是带宽受限?

## 四、第 2 步:判断瓶颈性质(roofline,屋顶线模型)

### 本节要回答的问题
MUL_MAT 慢,是因为"算不过来"(算力受限)还是"搬不过来"(带宽受限)?这决定优化方向完全不同。

### 方法:算算术强度,和"脊点"比

用第 1.3 节的概念:算出每个 MUL_MAT 的算术强度(AI,每搬运 1 字节要做多少次运算),再和硬件能力比较:

1. **算硬件"脊点"(ridge)**:脊点 = GPU 理论峰值算力 ÷ 内存带宽。
   - M2 峰值算力(FP16)≈ 5800 GFLOPs(每秒 5800 亿次运算)
   - 统一内存带宽 = 100 GB/s(每秒搬 100 GB)
   - 脊点 = 5800 ÷ 100 = **58 FLOPs/byte(每字节要做 58 次运算才算得过来)**
   - 含义:如果某个运算的算术强度 > 58,说明每次搬运都跟着足够多的运算 → 算力是瓶颈;如果 < 58,说明搬得太多算得太少 → 带宽是瓶颈。

2. **算实际 MUL_MAT 的算术强度**。从 profiling 拿到的真实形状(如权重 2048×8192、输入 2048×512)算出:

| MUL_MAT 形状(权重 × 输入) | 算术强度(AI) | 远大于 58? |
|---|---|---|
| q4_K 2048×8192 × 2048×512 | 1489 | 是(25 倍) |
| q4_K 2048×2048 × 2048×512 | 964 | 是(17 倍) |
| q6_K 8192×2048 × 2048×512 | 776 | 是(13 倍) |

3. **结论**:算术强度远超脊点 → **这是 compute-bound(计算受限),瓶颈是算力没跑满**。反过来说,优化带宽、缓存没意义,只能优化计算效率。

### 但还缺一个数:算力到底用满没有?

既然算力受限,那算力利用率高不高?计算(用的是无插桩的干净吞吐,排除计时误差):

- 一次 PP512 推理的总运算量(FLOPs)≈ **0.94 TFLOPs**(把所有矩阵形状乘起来求和,估算,误差 ±20%)
- 实际速度 = 总运算量 ÷ 实际耗时。q4_K 跑出 994.2 tok/s(每秒处理 994 个 token),那么 512 个 token 耗时 = 512 ÷ 994.2 ≈ 0.515 秒
- 实际算力 = 0.94 TFLOPs ÷ 0.515 s ≈ **1.83 TFLOPS**
- 利用率 = 1.83 ÷ 5.8 ≈ **31.5%**

### 本节结论
**瓶颈是算力受限,但算力只用了 ~31%——相当于发动机 300 马力只用了 90 马力。** 既然算力没跑满,理论上就存在优化空间。**下一个问题:算力为什么没跑满?**

---

## 五、第 3 步:提出三个候选假设

算力没跑满,可能的原因很多。我们挑三个最常见的、可以逐一用实验证伪(证明是假)的:

| 编号 | 假设 | 一句话 |
|---|---|---|
| **H1** | dequant(反量化)计算太贵 | Q4_K 权重要解压缩,解压缩指令摊薄了有效算力 |
| **H2** | kernel 的 tile(分块)配置不匹配 batch | 每个线程组处理的块大小和"512 行输入"不匹配,导致有些算力闲置 |
| **H3** | 访存停顿(stall) | 数据搬运的模式不好,GPU 等数据等太久 |

下面两节分别验证 H1、H2。H3 会在第 6 步的成本分解里间接回答。

## 六、第 4 步:验证 H1(dequant 是不是元凶)——本节是全文重点

### 本节要回答的问题
**如果 dequant(反量化)计算真的是元凶,那它到底占了多少时间?** 我们要得到一个"可证伪"的答案,而不是拍脑袋说"它很贵"。

我们分两步走:先"定性"(它有没有影响、影响多大范围),再"定量"(精确到百分之几)。

### 6.1 定性实验:三对照法(控制变量)

**思路**:用一个模型文件,分别转成三种"反量化复杂度"不同的格式,其他什么都不变,看性能差多少:

| 模型格式 | 反量化复杂度 | 权重内存占用(每权重位数 BPW) |
|---|---|---|
| **Q4_K**(原版) | 复杂:要解 4 位权重、还要处理缩放和偏移,分支多 | 5.18 bit |
| **Q8_0** | 极简:8 位权重只乘一个缩放系数 | 8.50 bit |
| **F16** | **完全不需要反量化**,权重直接就是 16 位浮点 | 16.0 bit |

**关键设计**:Q8_0 和 F16 的权重字节数比 Q4_K 多(8.5 和 16 vs 5.18)。如果瓶颈是带宽(搬运量),那么**字节越多应该越慢**;如果瓶颈是反量化计算,**反量化越简单应该越快**——这两个预测互相矛盾,结果会告诉我们真相。

用 `llama-bench` 跑同一个 pp512 基准:

| 模型格式 | pp512 吞吐(tok/s) | 相比 Q4_K |
|---|---|---|
| Q4_K | 994.2 ± 1.3 | 基准 |
| Q8_0 | **1094.8 ± 6.8** | **+10.1%** |
| F16 | **1208.4 ± 4.0** | **+21.5%** |

**结果解读**:
- **F16 字节最多(Q4_K 的 3 倍),却最快。Q8_0 字节多 64%,却比 Q4_K 快 10%。**
- 这就**排除了"瓶颈是带宽"**:如果是带宽,字节多的应该更慢,但事实正好相反。
- 剩下唯一能解释这种排序的,就是**反量化复杂度**:Q4_K 反量化最复杂→最慢,F16 不需要反量化→最快,严格单调。
- **所以 H1 方向正确:反量化确实拖慢了 PP,量级在 10%~21% 之间。**

> 补充一个反向证据,顺便确认了 TG 的结论:同样的三个格式跑 TG32,Q4_K=93.7、Q8_0=56.9、F16=36.4 tok/s——**正好反过来,字节越多越慢**。这恰好证明 TG 是带宽受限(搬运量大),和 PP 是完全不同的瓶颈。

### 6.2 定量实验:kernel 探针(直接量出反量化的成本)

**三对照实验只能告诉我们"反量化有影响,大概 10%~20%"**,但这里面其实混了两样东西:(a) 反量化的**计算**(解压缩的指令),(b) Q4_K 格式的**访存模式**(4 位权重读起来不规整)。我们想知道:单是"反量化计算"值多少钱?

**方法——探针(probe)**:直接改 Metal kernel 源码,把反量化那一步"跳过",用一个常数填进去,再测速。这是性能工程里的"反事实实验":**把怀疑的环节故意去掉,看性能变多少**。

具体改了一行(`mul_mm.metal` 里 `dequantize_func(x, il, temp_a)`,这行就是"执行反量化")。替换成:跳过真正的反量化计算,只从权重内存读 1 个字节塞进去(特意保留这次读取,是为了防止编译器发现"结果没用到权重"就把整个权重读取都优化掉,那样测的就不是反量化,而是"连权重都不读了",数据会失真)。

**结果**(同一台机器、同一个模型、同一个 pp512):

| 版本 | MUL_MAT 耗时(ms) | 相比原版 |
|---|---|---|
| 原版 Q4_K | 1028.8 | 基准 |
| **探针版(跳过反量化计算)** | **912.1** | **−11.3%** |
| F16(对照组,本来就没反量化) | 834.7 | −18.9% |

**结果解读——为什么 11.3% 是"反量化计算的上限"**:
- 把反量化计算**完全免费**(跳过它),MUL_MAT 从 1028.8 降到 912.1ms,快了 11.3%。
- 反过来说:**就算我们想出天大的办法把反量化计算优化到 0 成本,最多也只能快 11.3%**——因为剩下的 912.1ms 里还有权重读取、共享内存写入、矩阵乘指令等其他成本。
- 顺带一个交叉验证:探针版(912.1ms)几乎等于 Q8_0 对照组(923.7ms)。这很合理:Q8_0 的反量化本来就极简(≈免费),而探针版把 Q4_K 的反量化也弄到≈免费。两个独立途径得到接近的数,说明测量可信。

### 6.3 本节结论

- **H1 被否定为"主瓶颈"。** 反量化计算确实存在成本,但只有 ~11%——它重要,但不是"算力只用了 31%"的主因。
- **双缓冲(double-buffer)这类"把反量化计算藏起来"的优化,理论天花板就是这 11%,还要付出重构 kernel 的高代价,不划算**(这个权衡在第十节展开)。

## 七、第 5 步:验证 H2(形状是否匹配)

### 本节要回答的问题
如果是因为"512 行输入"这个 batch 太小,导致 GPU 每个线程组(threadgroup)的块状化(tile)没排满,那么**输入越大应该越快**。我们用实验验证。

### 方法
把输入 token 数从 128 一路加到 2048,看吞吐是否提升:

| pp(输入 token 数) | 吞吐(tok/s) |
|---|---|
| 128 | 964.5 ± 22.2 |
| 256 | 958.0 ± 47.1 |
| 512 | 994.2 ± 1.3 |
| 1024 | 975.8 ± 1.0 |
| 2048 | 923.5 ± 1.7 |

### 结果解读
- 输入从 128 翻到 2048(16 倍),吞吐基本稳定在 923~994,没有任何上升趋势。
- **如果 H2 成立(形状不匹配),增大 batch 应该让利用率明显上升——但事实是没有。**
- 说明 M=512 的输入大小已经足够喂饱 GPU,瓶颈不在"块太小、线程组不够"。

### 本节结论
**H2 被排除。** 算力利用率低不是 batch 形状造成的。

## 八、第 6 步:汇总——时间到底花在哪了(成本分解)

现在把第 4、6、7 步的结论拼起来。我们把 Q4_K 的 MUL_MAT(1028.8ms)拆成三段,每段用"减法"精确得出:

| 组成 | 计算方法 | 耗时(ms) | 占比 |
|---|---|---|---|
| **① F16 基线** | 直接测 F16 的 MUL_MAT | 834.7 | 81.1% |
| **② dequant(反量化)计算** | 原版 − 探针版 = 1028.8 − 912.1 | **116.7** | **11.3%** |
| **③ 4 位权重解包 / kernel 分支** | 探针版 − F16 = 912.1 − 834.7 | **77.4** | **7.5%** |
| **合计** | = 原版 Q4_K | **1028.8** | 100% |

**口径说明(诚实交代)**:
- 这张表的数字来自"带插桩(profile)"的测量,插桩本身会加约 9% 的同步开销,所以绝对时间偏大;**但**三个版本(Q4_K/探针/F16)是用同一个开关切换的,同步开销对它们是一样的,所以**相对差异(11.3%、7.5%)是可靠的**。
- ③这一项不是单一原因,而是"Q4_K 格式固有的成本减去反量化计算后的剩余"——包含 4 位权重不规整的读取、位解包指令、以及 kernel 里针对量化格式的分支判断。想拆得更细,需要更深入的 kernel 级探针(本文不做)。

### 三个组成各自说明了什么

- **① 占 81%:这是"不用反量化、权重规整"的 F16 也要花的时间。** 换句话说,MUL_MAT 的主要时间花在矩阵乘本身(和它的访存),而不是量化格式特有的东西。
- **② 占 11%:反量化计算的真实成本。** 已经用探针证实,是"上限"。
- **③ 占 8%:4 位权重格式固有的代价。**

### 回顾 H3
第三节提的 H3(访存停顿)在这张表里的体现,主要是 ③(4 位权重读取模式不规整导致的额外访存开销),量级 ~8%,同样是次要因素。

## 九、第 7 步:结论——真瓶颈是什么

### 9.1 核心结论

**PP 阶段 MUL_MAT 慢,主要不是任何"量化特有的开销",而是矩阵乘指令本身的利用率不够高。**

- 看第①项:即便用最干净的 F16(不反量化、读取规整),MUL_MAT 也要 834.7ms,对应算力利用率只有 **38%**。
- 这 38% 是 **ggml-metal 当前这个 MUL_MAT kernel 在这个 M2 上的实际水平**——它已经是社区长期优化的生产代码。
- 量化格式只额外带来了 ~19%(11% 反量化 + 8% 解包),都排在"次要"。

### 9.2 必须诚实说明的边界

- **38% 不是 M2 硬件的物理上限。** 它只是"当前 kernel 的水平"。可能存在更好的 kernel 写法(不同的分块、不同的调度)能把利用率提到更高——但这需要重写核心生产 kernel,难度和风险都很大,而且**没有简单实验能先证明"一定能提到多少"**。要确定 M2 的真实可达峰值,需要另外写一个独立的矩阵乘微基准(这属于未来的工作)。
- **31%~38% 的利用率有估算误差。** 计算利用率的分子(总运算量 0.94 TFLOPs)是形状估算,误差 ±20%。所以 31% vs 38% 的方向性可靠,具体数字是量级估计。

### 9.3 一句话总结
**"算力只用了三成"的主因,不是反量化(11%),而是矩阵乘 kernel 本身的指令效率(38% 就是这个 kernel 的现状)。** 想再快,只能向"提高矩阵乘指令利用率"要空间,而不是动反量化。

---

## 十、对优化的指导:什么值得做、什么不值得

| 优化方向 | 理论收益上限 | 实现难度 | 结论 |
|---|---|---|---|
| 优化 `dequantize_q4_K`(反量化函数) | ~11% | 中:与格式深度耦合 | **不值得作首选** |
| 双缓冲(反量化与矩阵乘重叠) | <11% | 高:需重构共享内存布局 | **不值得** |
| 调整 K 步长(NK) | 未验证,≤11% | 中 | 证据不足,收益上限低 |
| **提高矩阵乘指令利用率** | **~20%(追平 F16 的 38%)** | **高:重写生产 kernel** | 理论空间最大,但突破社区已优化的 kernel 难度极高、收益不确定 |
| 干脆换 F16 模型提 PP | +21%(仅 PP) | 零 | **整体不可取**:TG 会慢 61%,得不偿失 |

**工程建议**:在 M2 的 PP 路径上,与其押注"重写 MUL_MAT kernel"(高投入、收益不确定),不如把资源转向 TG 侧——那里存在一个**真实可复现、方向明确**的问题:ngl 部分 offload(只把前 1~8 层交给 GPU)时,吞吐出现性能谷底(见最初的数据扫描)。TG 是带宽受限,优化方向明确(减少搬运量),是更值得投入的下一站。

## 十一、方法论反思:我们怎么避免"把正常水平误判成可优化"

这次分析最值得带走的不是结论,而是**一条能防止误判的验证链**:

1. **roofline 只告诉你"范围",不告诉你"原因"。** AI >> 脊点说明是算力受限,但算力为什么没跑满,它不负责回答。
2. **对照实验能"定性",不能"定量"。** Q4_K/F16/Q8_0 三点对照证明了反量化有影响(10%~20%),但它分不清"反量化计算"和"4 位访存模式"各占多少。
3. **探针给出的是"上限"。** 把反量化计算完全跳过,得到 11.3%——这是它影响的上限。用"上限"来决策"值不值得优化",比猜可靠得多。
4. **判断"还有没有优化空间",一定要找一个"无瓶颈对照"当天花板。** 我们拿 F16 当这个对照——它没有反量化,是最干净的矩阵乘路径,而它也才 38%。如果只盯着"31% 利用率真低"就说"有空间",就会把 kernel 的正常水平误判成可优化的空间。
